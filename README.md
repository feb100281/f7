# FORMULA7 · Запчасти — хелпер отдела продаж

Django-приложение для отдела продаж запчастей на лодки и моторы.
Локальная версия: Python 3.12, SQLite, админка на [Unfold](https://unfoldadmin.com).

Что есть: импорт продаж из 1С, номенклатура с товарными группами, продажи в базе,
витрины DuckDB и дашборды аналитики, список команд с запуском из админки.

## Установка

```bash
bash install.sh          # клонирует репо в ./f7, ставит .venv, зависимости, .env, миграции, firstrun
bash install.sh mydir    # то же, в ./mydir
```

Если `install.sh` лежит в папке проекта — делает `git pull` и переустановку на месте.
Повторный запуск безопасен: `.env` не перезаписывается, `firstrun` ничего не задваивает,
суперпользователь создаётся, только если его ещё нет.

Последний шаг — данные: если продаж в базе ещё нет и папка из параметра `source` команды
«Импорт продаж из 1С» существует, скрипт предложит загрузить их сразу (`parse_sales`:
номенклатура → продажи → витрины). Если продажи уже есть — пересчитает витрины.
Сама база (`db.sqlite3`) и данные (`data/`) в git не хранятся.

Запуск:

```bash
source .venv/bin/activate
python manage.py runserver
```

Админка: http://127.0.0.1:8000/admin/ (корень `/` редиректит туда же).

## Данные: продажи из 1С

Команда «Импорт продаж из 1С» (`parse_sales`), параметр `source` — папка с xlsx-отчётами
«Продажи» (Регистратор → Номенклатура). Шаги:

1. xlsx → строки и документы (pandas), сверка с «Итого» каждого файла;
   сырые данные — `data/parquet/sales/sales_lines.parquet` и `sales_docs.parquet` (для разбора в DuckDB);
2. номенклатура (`catalog.Item`): новые артикулы, названия, группы по правилам (ручная разметка не трогается);
3. продажи в базу (`sales`): полная перезаливка;
4. витрины (`build_marts`) и статистика в карточках артикулов.

Шаги отключаются параметрами `write_parquet` / `sync_catalog` / `load_sales` / `build_marts` = false.

`kind` документа: `service` — наряд, `sale` — реализация, `retail` — розница,
`return` — возврат (кол-во и суммы с минусом), `correction` — корректировка.

## Витрины и дашборды

DuckDB выполняет SQL из `sql/marts/` (список `MARTS` в `marts/services/build.py`) в одном соединении
и пишет таблицы `mart_*` прямо в `db.sqlite3` — база подключена как схема `db`.
`_base.sql` создаёт temp view `lines` (строка продаж + документ + артикул + группа + месяц/сезон),
остальные файлы агрегируют уже его.

| таблица | SQL | зерно | для чего |
|---|---|---|---|
| `mart_sales_month` | `sales_month.sql` | месяц × канал × салон | Обзор, Салоны |
| `mart_group_month` | `group_month.sql` | месяц × группа × канал × салон | Товарные группы |
| `mart_service_month` | `service_month.sql` | месяц × салон (наряды) | Сервис |
| `mart_service_items` | `service_items.sql` | артикул × месяц × салон (только наряды) | Сервис: топ артикулов |
| `mart_season` | `season.sql` | сезон × месяц сезона × канал × группа × салон | Сезонность |
| `mart_item_month` | `item_month.sql` | артикул × месяц × канал × салон | детализация, будущий прогноз |
| `mart_item_stats` | `item_stats.sql` | артикул | поля статистики в номенклатуре |
| `mart_meta` | `_meta.sql` | одна строка | когда построено, последний месяц |

- Ключ агрегатов — `row_number()`, у `mart_item_stats` — `item_id`. Модели `managed = False`,
  FK с `db_constraint=False, on_delete=DO_NOTHING`.
- DuckDB пишет DATE в SQLite текстом — при чтении `mart_*` в SQL всегда `::date` / `::double`.
- В витринах группа артикула записана на момент пересчёта. Если менеджер переносит артикулы,
  дашборд показывает плашку «витрины устарели» и ссылку «Пересчитать».
- Пересчёт: сам в конце импорта или команда «Пересчитать витрины» (`build_marts`).
- Сезон — октябрь–сентябрь (сезон 2024 = окт 2024 – сен 2025).

Дашборды (sidebar «Продажи», `sales/dashboards/`, шаблоны `sales/templates/sales/dashboards/`):
Обзор продаж, Товарные группы, Сервис (наряды), Салоны, Сезонность. Фильтры — период
(12 мес., сезон, прошлый сезон, с начала года, всё, произвольный), салон, канал; сравнение — с тем же
периодом год назад.

Новая витрина: SQL в `sql/marts/` + строка в `MARTS` + unmanaged-модель + `makemigrations marts`.

## Прогноз выручки (forecast)

Prophet по двум рядам: **сервис** (наряды) и **реализация + розница**; «Всего» — сумма.
Выручка по дням, без возвратов и корректировок (`sql/forecast/docs.sql`).

Две команды (Система → Команды):

| команда | что делает | когда |
|---|---|---|
| «Прогноз: подбор параметров» (`forecast_tune`) | перебор параметров × rolling-бэктест, лучшие сохраняет, сразу строит прогноз | раз в квартал |
| «Прогноз: построить» (`forecast_build`) | прогноз на остаток месяца + N месяцев с параметрами последнего подбора | после каждой загрузки продаж |

**Бэктест.** Отсечки — начала месяцев в прошлом (по умолчанию каждые 2 месяца, последние ~1,5 года).
С каждой модель учится только на данных до отсечки и прогнозирует `horizon` месяцев; ошибка —
WAPE по месячным суммам (Σ|факт − прогноз| / Σ факт) на 1–3 мес. и на всём горизонте, по всем
отсечкам вместе. Побеждает минимум среднего из двух. «Prophet по умолчанию» считается всегда —
для сравнения.

**Сетка** (`forecast/services/engine.py`, `DEFAULT_GRID`, можно переопределить в `grid` у задачи):
окно обучения (`all`, с даты, последние N лет), порог выбросов (дни с документом крупнее —
пропускаются при обучении), `changepoint_prior_scale`, `seasonality_prior_scale`, сложение /
умножение, дни / недели. Подбор идёт в несколько процессов (`workers`, 0 — все ядра, кроме одного).

**Сравнение с фактом:**
- «Прогноз → Проверка на прошлом» — прогноз с каждой отсечки против факта, график и таблицы;
- там же «Сохранённые прогнозы против факта» — каждый «Построить прогноз» сохраняется, и когда
  месяц закрывается фактом, видно, насколько попали и был ли факт в коридоре;
- на «Прогнозе» можно выбрать старый прогноз — на графике и в таблице сразу будет факт.

Коридор — 80%: месячные суммы выборок `predictive_samples`, 10-й и 90-й процентили.

## Продажи в базе

`parse_sales` после номенклатуры загружает продажи в SQLite:

- `Department` — подразделение по префиксу номера (78УТ, 47УТ…), создаётся само, название — в админке;
- `SalesDoc` — документ: канал (`kind`: наряд / реализация / розница / возврат / корректировка), номер, дата, подразделение;
- `SalesLine` — строка: документ, **артикул (FK на `catalog.Item`)**, кол-во, выручка, себестоимость.

Группа, тип спроса и техника в продажах не хранятся — берутся через артикул. Перенёс артикул
в другую группу — все его продажи сразу считаются в новой группе (в админке, в запросах, в витринах).

Загрузка пока полная: таблицы продаж очищаются и заливаются заново. Данные продаж в админке
только для просмотра; правятся только подразделения.

## Номенклатура и товарные группы

- **Товарные группы** (`ItemGroup`) — начальный список из `catalog/rules.py` создаёт `firstrun`.
  Дальше группы ведут менеджеры: название, тип спроса, порядок, описание; можно добавлять свои.
  Код группы связывает её с правилами — после создания не меняется.
- В списке групп каждая строка **раскрывается** — топ-25 артикулов группы по выручке
  и ссылка на все артикулы группы.
- **Номенклатура** (`Item`) — группа меняется прямо в списке (колонка «Группа»), массово
  (отметить строки → «Назначить группу» + выбрать группу в панели действий) или в карточке.
  Любая ручная смена → «Вручную»: импорт и пересчёт по правилам такие артикулы не трогают.
  Вернуть автоматику — действие «Вернуть группу по правилам».
- **Правила** — `catalog/rules.py`: (группа, ключевые слова) сверху вниз, первое совпадение;
  сверху узкие исключения («OIL SEAL» → сальники), ниже широкие. Масло — только если в названии
  есть объём/вязкость/XPS. После правки правил — команда «Пересчитать товарные группы».
- **Тип спроса** группы: расходники ТО, износ, ремонт, кузов, аксессуары, крепёж — основа
  для выбора метода прогноза и матрицы must have.
- **Техника** (`Platform`): квадро и SSV, снегоходы, гидроциклы, двигатели Rotax, общее.

## Как добавить команду

1. Файл `<app>/management/commands/my_cmd.py`:

   ```python
   from core.management.base import JobCommand
   from core.models.jobs import JobTypes

   class Command(JobCommand):
       help = "Что делает"

       # карточка в «Списке команд»
       job_name = "Моя команда"
       job_type = JobTypes.ETL
       job_description = "<p>Описание для админки</p>"
       job_param = {"source": "~/папка"}   # параметры по умолчанию

       def run(self, params: dict):
           self.step("Шаг 1")
           folder = params.get("source")
           ...
           self.ok("Готово")
   ```

2. `python manage.py sync_jobs` (его же зовут `firstrun` и `install.sh`) находит все
   `JobCommand` с `job_name` во всех приложениях и заводит карточки. У существующих обновляет
   название, тип и описание; параметры, поправленные в админке, не трогает.
3. В админке: Команды → «Запустить». Вывод пишется в `media/jobs/logs/<команда>.log`,
   открывается кнопкой «Открыть лог».

Руками: `python manage.py my_cmd` (параметры берутся из записи в списке команд).
